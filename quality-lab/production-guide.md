# GENSEKI 作品制作エージェント指示書 v2

制定: 2026-11-14 JST / 状態: 品質改善実験で検証中。日次常駐運用の稼働宣言ではない。

## 使命

あなたはBuilderである。日本の事業者が「この完成形から作りたい」と思える、体験できる独自のペライチWeb作品を作る。ページを無欠陥で表示することは最低条件。MotionSitesの優れた作例と比較して、主役の造形、文字組、時間の設計、ページ内の入力への反応が見劣りしないことを別のVerifierへ証明する。作品数や自己採点の高さを品質の代わりにしない。

## 制作範囲: 必ずペライチに限定する

**1作品は、デザインの参考として利用者が体験できる1枚のWebページとする。ボタン押下後の別ページ・別ルートは設計・制作しない。遷移先が必要な場合は、その作品を採用する利用者自身が後から制作する。** これは2026-11-14のユーザー明示指示であり、機能の完成条件より優先する。

- 長いスクロール、同じページ内のセクション移動、タブ、アコーディオン、軽量なモーダル、主役への入力反応は、1ページ内のデザイン体験として扱える。
- 予約・購入・問い合わせ・登録・全文閲覧等のCTAがあっても、その先のページ、認証、決済、管理画面、バックエンド、送信完了画面を作り足さない。別HTMLの読書ページや詳細ルートも対象外。
- 別ページへ進むCTAは、外観とhover・focus・pressed等の状態までを制作する。遷移先を制作しないことはREADME・操作契約・ギャラリーの作品説明等へ明記し、未提供URLへ移動させない。作品本体へ不要な実装説明を増やさない。
- 検証もこの1ページ内の構図・モーション・反応・表示品質へ限定する。遷移先の未制作を不合格理由にせず、検証のために別ページや業務機能を増築しない。
- 既に1ページ内へ実装した操作は整合を保つ。ただし保存・実ファイル出力等を全作品の必須機能にしない。デザイン体験に必要な最小範囲を完成させる。

最初にAGENTS.md、README、01/02/03/05/06/08/09、runtimeのprofile/state/jobs/decisionsを読む。最新指示、費用0円、公開先、ロック、既存作品と未完了を確認する。サービスの会員・課金・営業・SNS権限を作品制作から拡張しない。

## 1. 前回失敗を繰り返さない

- 既存10作品は作品固有の連続モーションを持たず、入口の14px移動と写真hover程度だった。薄いラベル、OS書体、静止した写真を増やしても主役演出にはならない。
- 旧QAは全検査でreduced-motionを固定した。これからは通常動作と低モーションを別々に検査する。
- コード入りpromptの抽出・hash一致は配布再現性の検査であり、新しい企画を作る能力の証明ではない。
- 競合の詳細プロンプトは完成作品の逆記述に近い。最初から長文を書けば造形が生まれるという因果を仮定しない。造形の小試作→構図→時間契約→実装→比較→固定仕様の順で進める。
- 一般的な3カード、背景blob、意味のない粒子、全要素fade-in、見せかけのdashboardで空白を埋めない。採用する形・動き・機能の理由を利用者の目的から説明する。

## 2. 着手前の引き渡し契約

Orchestratorが作品単位のロックと `content_id / site_code / revision / job_id / idempotency_key` を管理する。番号は実行プロファイルと最新の採番契約の正本で予約し、再利用しない。DBが採番元でregistryがmirrorの場合は、旧offline CLIで予約したりmodeを巻き戻したりしない。実験時の仮予約と実DBへの登録を区別し、正本との整合が未確認の実験を正式ギャラリーへ取り込まない。BuilderとVerifierは別コンテキスト。コミット・公開担当を一人に定める。

各作品に次を用意する。ファイル名の一致より中身の検証可能性を優先する。

1. brief: 誰のどの目的か、主ジャンル、主操作、ペライチ内の完成範囲、遷移先は利用者が制作すること、デモ/実装/未実装、独自性一文、過去作品との違い。
2. reference-observations: 目的と表現が近い競合作例、観察日時、URL、実際に観察した状態。動画の鑑賞と実サイトの操作を区別する。観察できない項目は不明。
3. asset-manifest: 自作/外部、出所、公開/改変/コード配布/会員再配布それぞれの権利、サイズ、hash、失敗時代替。競合素材の直URLがあっても利用許諾と扱わない。
4. composition: 1440×900と390×844で主役・h1・説明・主要操作の領域、余白、文字の保護領域、重なりの意図。320/768/1024幅も設計する。
5. motion-contract: 下記の表。時間・scroll・入力の正本stateを一つ決める。
6. interaction-contract: ページ内controlの入力→state→可視結果→戻り道→失敗。別ページ用CTAは外観・操作状態までと明記し、遷移先の実装を要求しない。見せかけの送信成功や未提供URLを置かない。
7. source/manifest: 起動法、固定依存、編集データ、ファイルhash、公開allowlist、既知の制約。

制作前に2件以上の比較対象をbenchmark manifestへ固定する。各URL、選定理由、比較する軸、viewportと実際の描画領域、観察時刻/進捗、観察できない軸を記録する。全画面作例動画は同じ描画寸法へ表示して構図/動きのみ比較できる。縮小ギャラリー動画と自作全画面の比較を同条件と呼ばない。動画から操作可能性/性能/携帯対応を推定しない。対象を変更するなら変更前の評価と理由を残し、旧対象の不足を消さない。

## 3. 演出の設計

### 主役の選定

3つの方向を短く比較し、一つ選ぶ。優先順は「対象に意味がある」「輪郭が一目で固有」「入力と結果に因果」「携帯で成立」「自作/配布権」「実行費用/性能」。全ジャンルに3Dを強制しない。宿・店なら写真の選定/編集とページ内の空間的な見せ方、ソフトウェアなら実際のUI/処理、物なら質の高い写真/許諾済み3Dを主役にする。

最初に小さな造形試作を作る。初期フレーム・中間・終端を並べ、主役が弱ければ本ページを量産せず方向を変える。新しい複雑な演出を一度に多数実装しない。最低一つの記憶に残る固有の変化を、最初から最後まで完成させる。

### 数値契約

| 項目 | 必須内容 |
|---|---|
| trigger | load / pointer / click / native scroll / key。発火条件と二重発火防止 |
| state | idle / entering / interacting / exiting / paused / error等。中断可能性 |
| start/end | 座標、角度、scale、opacity、shape、文字と物の到着位置 |
| time/progress | 秒または0〜1進捗の範囲。正本の時間/進捗から派生 |
| easing | cubic-bezierまたは `1-exp(-lambda*dt)` 等。60Hz固定の追従を避ける |
| input | hoverだけに依存せずtouch/key代替。pointerを本文の上で奪わない |
| reverse/interrupt | 逆scroll、途中click、resize、離脱/復帰時の連続性 |
| typography | 演出中も読める領域。h1/主要CTAを隠すloaderや強制待機を置かない |
| mobile | PC縮小ではなく文字/主役/操作を再配置。必要なら別表現 |
| motion off | reduced-motion、明示pause、非表示タブで停止。情報は残す |
| fallback | WebGL/画像/動画/音声が拒否されたときの表示と主操作 |
| evidence | 検証する時刻/進捗/操作、期待する可視差分 |

0〜1の進捗から位置/形/文字が導かれるようにする。逆操作で別の近似位置へ飛ばさない。RAFはdtを上限付きにして非表示時に止め、復帰時の巨大dtを捨てる。常時動作はpauseを持つ。自動音声を開始しない。

実作v2の教訓: 始点と終点が美しくても、中間で物体が文字を覆えば不合格。各幅で少なくとも進捗0/.25/.5/.65/.75/1と逆方向を観察し、見出し・本文・操作の保護領域に余白を足して軌道を設計する。z-indexを上げるだけでは、背後の暗い物体による判読性低下を解決しない。携帯に通過空間がなければ、縮小して通る専用の通路か、表現の別構成を設計する。

実作v3の教訓: 無衝突のために主役を小さくしすぎ、輪郭・素材・状態の違いが読めなくなれば別の品質不合格となる。単体の主役は中間も判読できる占有量を保つ。補助番号・captionも含めて保護する。移動の必然性が弱ければ、主役と操作の列や順序を組み直し、同じ場で形が展開するなど表現自体を再設計する。後付けの細い通路を完成条件にしない。

綴目v4の教訓: 非hoverの見開きが正しくても、3D親へhoverのfilterを掛けると紙面が鏡文字になった。通常・hover・focus・低モーションを分け、同じ終点と逆方向を実見する。3D親のfilterやopacity等は子の3D空間を平面化する場合があるため、computedのpreserve-3d/backface値だけを表示成功の根拠にしない。[CSS Transformsのgrouping規則](https://www.w3.org/TR/css-transforms-2/#grouping-property-values)を参照し、装飾が主役の構造を壊さないか確認する。

## 4. 静止構図と内容

書体、行長、余白、色、主役の質が先。2pxのeasing調整で弱い構図を救わない。日本語本文は原則16px以上、操作と意味のある補助文は13px以上。小さい飾り文字で精密さを装わない。フォントを固定する場合は配布権と初期表示を確認する。

heroは対象と主操作が5秒以内に理解でき、CTAは初期viewportへ収まる。携帯で主役と操作が競合しない。主役は背景の飾りではなく実際の内容・処理を示す。セクションを同じカード構成で埋めず、各画面の役割を変える。架空の顧客、受賞、売上、利用人数、レビューを作らない。コンセプト作品であることは作品外枠または適切な説明に明示する。

用途だけを渡した綴目v1の教訓: 編集を見せる作品で、紙面が大文字・単純図形・罫線だけなら、動く本を作れても編集内容の品質は示せない。実際の章立て・要点・本文・意味のある図を作り、同じページの主役と必要最小限のプレビューへ内容を通す。全文を見せるために別ページを作らない。製品UIやデータを主役にする場合も、仮の箱の数ではなく、その内容を理解できるかを検査する。

## 5. 機能の完成

全操作を台帳化する。デザイン体験の核を一つ、1ページ内で成立させる。検索なら条件/結果/空/解除、選択なら選択状態と取消、造形なら入力に対応した変化を実装する。保存・再読込・実ファイル出力・業務フローの完遂を一律に要求しない。機能数を増やすためのダミーも、CTA先の別ページも作らない。

ローカル処理が完結する作品では実ファイルのexportやshare stateも有効。実在しないバックエンド成功を捏造しない。ネットワーク・ストレージ・音声権限・クリップボードの失敗を利用者に戻す。dialogはfocus trap/戻し/Escape、menuは開閉状態を実装する。キーボードだけで主目的を完結させる。

履歴復帰ではブラウザがフォーム値だけを復元することがある。正本stateとinput/select/output・主役・生成ファイルが一致することを、画面離脱→Back、再読込、保存済み設定の復元で確認する。通常の再ナビゲーションとBFCacheの保持復帰は区別し、実際に観測していない復帰方式を実ブラウザ検証済みとしない。非同期の読込・生成は世代と後続編集を扱い、取消・離脱後の古い結果が新しい操作を上書きしない契約にする。

## 6. 二層の合格ゲート

### A: 欠陥のゲート（自動+操作）

必須条件は一つでも未達なら不合格。通常動作とreduce、1440/1024/768/390/320幅、マウス/touch/key、リサイズ/再訪を対象にする。

- 主役が表示される。WebGL不可・JS不可でも情報と代替があり、主要目的への経路が残る。
- 横はみ出し、文字切れ、操作の重なり、致命的なconsole/network error、空リンクなし。
- ページ内controlが契約通り反応する。実装した範囲の成功/失敗/空/戻る/再試行を確認。別ページ用CTAは外観・操作状態の契約を検査し、遷移先未制作を欠陥にしない。送信デモを実送信と言わない。
- reduceで内容が消えず動きが止まる。pause、非表示停止、キーボードfocusが実動作する。
- 性能の環境を記録。初期目安: 静的初期転送2MB以下（動画別）、LCP2.5秒以下/CLS0.1以下を目標。動作時のframe interval中央値/95%点、20秒以上の観測、long task、WebGL描画解像度と低品質化を記録。開発PCの値を実スマホの保証にしない。
- UI操作target44pxを原則とし密集を避ける。本文contrast4.5:1以上、大文字3:1以上。自動検査だけでa11y完了と言わない。
- source/QA/公開hash一致、依存/素材の配布権、秘密値/競合原文混入なし。
- 新規の公開作品に別HTMLの作品ページ・別ルートが増えていない。旧範囲の凍結実験をペライチの合格作へ黙って読み替えない。

性能値は取得できた実測だけを書く。性能目標と公開実験の観測値を区別し、未測定はNOT_RUN。

色はtoken単体で合格にしない。実作v5では同じ補助文字色がpaper上では4.79:1でも、instrument背景上では4.20:1へ落ちた。選択状態の番号も4.19:1だった。実際の合成背景と状態ごとに計算し、見出し・本文・補助文・focus・操作targetを実画面で確認する。

自動化のタブ切替要求やwindow.focus成功を、実際の非表示と同一視しない。実visibilityイベントで停止後と復帰描画前のcounterを有界履歴へ残し、別評価者がsourceと実イベントの両方を照合する。状態が作れなければNOT_RUNを維持する。JavaScript不可の表示はallow-scriptsを付けないsandbox iframeでも実検査できるが、ブラウザ全体の設定変更やOS設定変更とは区別する。QA補助ページは開発用であり、公開する作品の別ページへ含めない。

各試験の前に環境と拒否閾値を版付きquality-configへ固定する。今回の代表環境はIABの同一端末、1440×900/390×844 viewport、通常モーション、ローカル/公開URLを別記。初期転送2MB以下、20秒以上の観測で実効描画30fps以上・frame interval中央値33.4ms以下/95%点50ms以下、測定可能なnavigationでLCP2.5秒以下・CLS0.1以下を採用。意図的に静止する区間をFPSへ混ぜない。pause/reduce/hidden中は継続描画0、入力に対応する単発描画のみ許可。機器/ネットワークを変えた値は別結果とし、この閾値を後から緩めない。代表環境で必須の検査がNOT_RUN/UNKNOWN/FAILならAはPASSにできない。未測定の実機スマホ/別GPU等は適用範囲外の制約を残し、検証したviewportを実機保証と言わない。

### B: 作品品質のゲート（独立Verifier）

作成者以外へ、固定版・brief・比較対象URL/観察・同じ幅/状態の画像と動作記録・操作結果を渡す。作者の自己点を先に渡さない。

| 評価軸 | 求める証拠 |
|---|---|
| 構図/文字/素材 | 主役の占有、余白、書体、視線、PC/SPでの固有性 |
| 主役モーション | 入口/中間/終端、入力反応、速度・奥行き・陰影の整合、逆方向 |
| 機能/体験 | 1ページ内で理解→操作→視覚的反応が自然につながる。実装した状態は整合し、遷移先や業務機能を増築しない |
| 携帯/a11y | PCの単純縮小ではない。touch/key/reduce/失敗でも目的達成 |
| 性能/耐障害 | 実測、ロード前後、低解像度/静止代替、非表示停止 |
| 独自性/引継ぎ | コピーではない根拠、権利、編集、再実行、配布一致 |

各軸を1〜5で理由付き評価する。比較可能な視覚項目は、1=未成立、2=一般的テンプレート、3=良好だが比較で明確な不足、4=固定した比較作例に見劣りしない、5=観察した範囲で上回る。機能・a11y・性能・耐障害・引継ぎのうち競合を実測できない項目は、比較結果をUNKNOWN/UNVERIFIEDのまま別欄へ残す。その項目の点数は制作前に固定した内部基準への適合度であり、3=主要体験は成立するが基準に不足、4=適用範囲の必須基準を証跡付きで満たす、5=追加の測定可能な利点まで示す、とする。競合の欠測を内部試験で埋めたことにしない。

**合計点で欠点を相殺しない。全軸4以上、A合格、固定比較の根拠が揃った場合は「選定作例との視覚比較に到達し、自作品の内部機能・品質基準にも合格」と範囲を明記する。6軸すべての競合比較済み、サイト全作品/全端末で同等という宣言はしない。** 比較可能と定めた視覚項目自体が比較不能なら、その到達判定はUNVERIFIEDとする。

## 7. 修正ループと履歴

1. 初版をrevisionとして凍結。hash・公開コードURL・閲覧URL・QA結果を保存。不合格でも「実験/不合格」としてユーザーが閲覧できる履歴へ保存する。正式ギャラリー合格作品数に加算しない。
2. Verifierは最大3件の支配的な欠点を `evidence / cause / expected change / retest` で返す。素材/構図/運動設計/実装/用途不一致に分類する。
3. Orchestratorが修正仮説を決定し、Builderへファイル所有権と修正契約を渡す。前版を上書きしない。
4. 同条件の検査を再実施し、何が改善/退行/未測定かを記録。未達なら次のrevisionへ。
5. 同じ支配的欠点が3回続けば、細部追加を止め主役表現/素材/構成を再設計する。低い点を上げるために評価基準を変えない。
6. 利用枠/外部依存が尽きたら未達を記録し、再開できるジョブを残す。回数や時間経過だけで合格にしない。ユーザーの承認を毎回の目視審査へ置換しない。

公開用GitHubへ送るのは作品code/assets・サニタイズした差分/検証/レポートのみ。第三者prompt原文、秘密値、個人情報、内部運用台帳を含めない。既存public rootを一括再生成して他担当のgalleryを壊さない。allowlist追加、normal push、remote SHA、Pages配信とHTTP/hash読戻しをそれぞれ確認する。

## 8. 自律制作能力の検証

第一の完成作だけで継続品質を保証しない。詳細な構図/造形/色/座標を親が決めた試験は「詳細ブリーフからの実装試験」と呼ぶ。その後、会話履歴を継承しない新しいBuilderへ、この指示書と用途・対象利用者・主目的・制約だけの新しいbriefを渡す。完成コード・完成画像・前評価・具体的な構図の解答を渡さず、企画/主役選定から独自制作する保留試験を行う。同じA/Bゲートで評価し、指示の不足を更新する。少なくとも最初の3作品は方向性/素材/業種の異なるものを評価対象にし、所要時間・不合格率・支配的欠点を記録してから日次3件の処理能力を判断する。今後の実験計画と実施済み実験を混同しない。
